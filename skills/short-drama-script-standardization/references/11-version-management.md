# 11 版本与修改管理

标准化的价值一半在结果，一半在"能追溯"。

## 11.1 版本状态词

| 状态 | 含义 | 谁产出 |
| --- | --- | --- |
| `draft` | 原稿/初稿，未处理 | 编剧 |
| `standardized` | 已完成格式标准化，内容未改动 | 本 Skill |
| `revised` | 已按意见修改内容 | 编剧 |
| `reviewed` | 已通过内部审读/评审 | 审稿 |
| `final` | 交付版 | 项目负责人 |

## 11.2 版本号规则

```
主版本.次版本   →  v1.0
```

- 主版本：内容结构发生实质变化（增删场次、改剧情）。
- 次版本：仅格式、标注、错字、局部措辞调整。
- 标准化本身若未改内容，版本为 `v1.0 standardized`，不因格式升级到 v2。

## 11.3 文件命名

```
项目名_第NN集_vX.Y_状态_YYYYMMDD.md
项目名_全稿_vX.Y_状态_YYYYMMDD.md
暗涌_第03集_v1.1_standardized_20261101.md
```

多文件交付时保持前缀一致，便于排序与打包。

## 11.4 修改记录字段

| 字段 | 说明 |
| --- | --- |
| 编号 | 与审查报告编号对应 |
| 位置 | 集-场 + 元素定位 |
| 类别 | A/B/C |
| 修改前 | 原文摘录 |
| 修改后 | 改后文本；建议未采用时写"未改" |
| 原因 | 依据（规范条款/用户确认/上下文推定） |
| 影响范围 | 单处/多处（多处写明数量） |
| 状态 | 已修复/待确认/未采用 |
| 操作者 | AI 标准化 / 用户决定 |

模板见 `assets/change_log_template.md`。

## 11.5 差异说明（给用户看的摘要）

不要只丢一份修改记录，要给出可读摘要：

```
本次处理：暗涌 第01–06集（共 52 场）
原稿版本：暗涌_全稿_v0.9_draft_20261020
处理结果：v1.0_standardized
格式修复：318 处（其中署名统一 41 处、符号统一 96 处、标点 121 处、空行 60 处）
内容改动：0 处
建议未采用：12 条（见报告 B 组）
待用户确认：9 条（见报告 Q 组）
未覆盖：第07–12集未提供
```

数字要真实可核对，不能估算。

## 11.6 归档内容

一次完整交付应归档：

1. 标准化剧本
2. 结构清单
3. 质量审查报告
4. 修改记录
5. 待确认清单
6. 制作交接说明
7. 原稿副本（只读留档）
8. 本次使用的规范卡（格式约定快照）

规范卡快照很重要：下一个人要知道"当时按什么规则统一的"。

## 11.7 规范卡（临时规范快照）

```
项目：暗涌
集号写法：第01集
场号写法：1-1（集号不补零）
场景标题：场号 时间 内/外 地点
动作标记：△
标注符号：【音效：】【字幕：】【切至：】
OS/VO 定义：OS=剧中人画外声，VO=叙述者
人物行：人物：A、B
对白：人物（提示）：换行
特殊约定：车内一律标"外"
生效范围：第01–06集
```

每次任务开始时写一次，交付时随档保存。

## 11.8 多版本并存处理

用户给多个版本时：

1. 先确认基准版（通常最新且最完整），写入规范卡。
2. 其余版本只做差异参考，不混合取材。
3. 若用户在旧版上做了手改，而新版没有：把旧版独有内容列为"差异待裁决"，不擅自合并。
4. 差异清单格式：`位置 | 旧版内容 | 新版内容 | 建议`。

## 11.9 撤销与回退

- 每完成一个大阶段（建账、施工、复核），保留一个中间稿。
- 用户否定了某项修改时，从中间稿恢复该处，不手工反改（易错）。
- 修改记录中标注 `已撤销`，不删除记录。

## 11.10 版本管理禁忌

| 禁忌 | 后果 |
| --- | --- |
| 覆盖原稿 | 失去回溯能力 |
| 文件名不带版本与日期 | 分不清哪个是交付版 |
| 修改记录事后补写 | 漏记、错记 |
| 用"最终版""最终版2""真最终版" | 无法排序 |
| 只交剧本不交报告 | 用户不知道改了什么 |
