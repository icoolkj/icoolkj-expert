# 10 连续性与创作状态管理

## 1. 为什么必须建台账

长篇写到 50 万字，作者对前文的记忆会衰减到 60% 以下。凭印象写作必然出现：

- 人物年龄对不上（三年前十八岁，现在还是十九）。
- 人物知道了不该知道的事。
- 死过的人又出现。
- 伤势自动痊愈。
- 伏笔永远收不回。

台账不是形式，是长篇能不能写完的基础设施。

## 2. 十二个检查维度

| 维度 | 检查内容 | 常见错误 |
|---|---|---|
| 人物年龄 | 出生年 + 当前故事年 | 角色年龄停滞 |
| 人物身份 | 头衔、职务、所属势力 | 已撤职仍在任 |
| 人物关系 | 称谓、亲疏、是否已决裂 | 吵架后仍用昵称 |
| 人物位置 | 此刻在哪，怎么来的 | 一天之内跨越千里 |
| 身体状态 | 伤、病、疲劳、饥饿 | 重伤后立即激战 |
| 故事时间 | 绝对日期 + 相对间隔 | 一夜之间过了三天 |
| 事件顺序 | 因果先后 | 结果先于原因 |
| 信息可见性 | 谁知道什么 | 信息越界（最致命） |
| 物品归属 | 谁拿着，什么状态 | 丢了的刀又出现 |
| 规则边界 | 能力限制、代价 | 临时放宽 |
| 势力状态 | 实力、立场、控制区 | 被打残后立刻满血 |
| 伏笔状态 | 已埋／已收／已废 | 悬而不决 |

## 3. 信息可见性表（最重要）

长篇崩坏 70% 来自信息越界。必须维护一张"谁在第几章知道什么"的表。

| 信息 | 首次出现 | 苏瑾 | 陆沉 | 船夫 | 巡夜队 |
|---|---|---|---|---|---|
| 匣子在箱中 | CH-0009 | CH-0009 | CH-0011 | CH-0012（猜） | 未知 |
| 巡夜队受人指使 | CH-0012 | CH-0012 | 未知 | 未知 | 全体 |
| 陆沉的身份 | CH-0003 | 未知 | 自知 | 未知 | 未知 |

写对话前查表：**说话的人此刻知道吗？** 不知道，就不能说。

## 4. 时间线管理

### 4.1 绝对时间轴

给故事设一个"第 0 天"，所有事件用 D+n 标记。

```
D-30  陆沉离开北境（前史）
D0    苏瑾抵达渡口
D0    夜渡（CH-0012）
D1    抵达对岸，遇伏（CH-0013）
```

### 4.2 相对间隔

每章记录"距上一章多久"。连续多章同一天时，要写清时刻。

### 4.3 常见时间错误

| 错误 | 检验 |
|---|---|
| 行程时间不实 | 地图距离 ÷ 交通方式 ÷ 天气 |
| 季节错乱 | 记录季节锚点（第一场雪、麦收） |
| 年龄算错 | 出生年 + 当前年，不靠心算 |
| 同一时刻两地 | 并行事件必须时间对齐 |

## 5. 冲突处理流程

发现矛盾时**不得静默修正**。按四步：

```
1. 定位：哪两处冲突，分别在哪一章
2. 定性：是设定冲突、事实冲突，还是记忆偏差
3. 影响：涉及哪些人物、伏笔、后续章节
4. 方案：给出 2–3 个修法，说明各自代价，请用户裁定
```

修法优先级：

| 方案 | 代价 | 何时用 |
|---|---|---|
| 改后文 | 小 | 前文已发表，后文未写（首选） |
| 改前文细节 | 中 | 冲突在细节而非情节 |
| 补解释圆场 | 中 | 冲突可被叙事吸收（如"他记错了"） |
| 改设定 | 大 | 设定本身错了，且影响未扩散 |
| 推翻重写 | 最大 | 结构性错误，必须早发现 |

**原则：优先改还没被读者看到的部分。**

## 6. 设定变更流程

用户要改前文某设定时：

```
1. 列出该设定在当前正文中的所有引用点（章、段）
2. 列出依赖它的剧情节点
3. 列出依赖它的伏笔
4. 评估改动后哪些章需要修
5. 给出「最小改动方案」与「彻底重写方案」
6. 等用户选择
```

不做影响面分析就改设定，是长篇崩盘的第二大原因。

## 7. 章节状态快照

每章写完，更新六个字段：

```
CH-0012 夜渡
时间：D0 子时—寅时
地点：LOC-014 老渡口 → 河心
在场：苏瑾、船夫、（巡夜队远处）
结束状态：苏瑾在河心，船夫死，匣子在身，右臂伤重
新增信息：巡夜队受人指使
未解决：谁指使；陆沉在哪
```

这六行是写下一章时唯一必读的东西。

## 8. 伏笔清算（每 20–30 章一次）

| 检查 | 动作 |
|---|---|
| 已收伏笔 | 标 `已收`，确认回收是否给了解释 |
| 超 40 章未提醒 | 加一次提醒，或标 `已废弃` |
| 提醒过 2 次仍未收 | 尽快安排回收，读者已记住 |
| 计划回收章已过 | 重新排期或废弃 |

**给用户的清算输出**（简明版）：

```
伏笔清算（截至 CH-0060）
在途 7 条：FORE-011（埋 12，提醒 19/31）、FORE-015（埋 44，未提醒）…
超期 2 条：FORE-004（埋 8，计划 40 收，现 60 未收）→ 建议 CH-0063 收
已收 12 条
建议废弃 1 条：FORE-009（与主线无关，回收成本高）
```

## 9. 冷启动（隔很久回来写）

四步，十分钟：

1. 读**上一章最后 800 字原文**（不要读摘要，摘要没有语感）。
2. 读上一章状态快照（六字段）。
3. 读当前卷纲 + 本章 Brief。
4. 读伏笔在途清单。

**不要**重读全书。会陷入"这里要改"的瘫痪，且语感被洗掉。

## 10. 台账维护脚本

见 `scripts/story_state.py`。核心命令：

```bash
# 初始化（一次）
python scripts/story_state.py init --dir ./novel --title "书名" --genre "玄幻" --pov "第三人称限知"

# 每章完成后追加
python scripts/story_state.py chapter --dir ./novel --no 12 --title "夜渡" \
  --summary "苏瑾夜渡，船夫死，匣子在身" \
  --chars "苏瑾:右臂伤重,河心|船夫:死" \
  --events "巡夜队封锁渡口;船夫认出匣子" \
  --fore-add "巡夜队受谁指使" --fore-close "FORE-004" \
  --open "陆沉下落"

# 查看进度与人物状态
python scripts/story_state.py status --dir ./novel

# 生成下一章承接单
python scripts/story_state.py brief --dir ./novel

# 查看久未触碰的伏笔
python scripts/story_state.py fore --dir ./novel --stale 20
```

脚本不可用时，用 `11-novel-templates.md` 的 Markdown 台账，功能等价。
