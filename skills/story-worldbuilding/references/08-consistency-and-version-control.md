# 08 一致性检查与版本控制

## 1. 一致性检查的十个维度

| # | 维度 | 检查方法 | 典型问题 |
|---|---|---|---|
| 1 | 时间 | 所有事件落到绝对时间轴 | 两件事同时发生在异地同一人身上 |
| 2 | 年龄 | 出生年 + 事件年交叉验算 | 年龄与经历不匹配 |
| 3 | 距离 | 路线耗时是否与情节节奏匹配 | 三天路程当天往返 |
| 4 | 信息 | 对照认知矩阵 | 人物说出他不知道的事 |
| 5 | 能力 | 对照规则卡的使用限制 | 关键时刻限制消失 |
| 6 | 资源 | 对照产出与消耗 | 稀缺资源随手可得 |
| 7 | 关系 | 对照关系表状态 | 昨日仇敌今日托付性命且无过渡 |
| 8 | 因果 | 事件链是否有断点 | 结果无原因 |
| 9 | 行为 | 行为是否符合动机与恐惧 | 人物做出违背性格的选择 |
| 10 | 版本 | 新旧设定是否冲突 | 旧章设定被新设定否定 |

## 2. 检查执行顺序

按"修复成本从低到高"排序执行：

```
编号与引用 → 时间 → 年龄 → 距离 → 能力 → 资源 → 信息 → 关系 → 因果 → 行为
```

原因：前面的错会污染后面的判断。时间错了，年龄和因果必然跟着错。

## 3. 冲突分级

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 硬冲突 | 同一事实两个互斥版本（人已死又出场） | 必须修复，不修复不能交付 |
| P1 结构冲突 | 规则被违反，但可用例外解释 | 补例外条款或改情节 |
| P2 张力冲突 | 逻辑成立但削弱强度（资源太充足） | 收紧设定 |
| P3 观感问题 | 不矛盾但显得随意 | 记录，择机优化 |

只有 P0 与 P1 需要在交付前解决。不要为了 P3 反复返工。

## 4. 冲突处理流程

**绝对禁止：发现冲突后自行选一个版本覆盖另一个。**

```
① 定位：冲突双方分别出自哪条设定/哪段正文
② 分级：P0/P1/P2/P3
③ 影响面：列出受影响的 CHAR / FACTION / EVENT / RULE / 章节
④ 方案：给出 2–3 个可选修复方案，每个方案说明代价
⑤ 请示：由用户决定，专家不代替决定
⑥ 记录：写入变更记录，标注版本
```

### 修复方案的三条常见路径

| 路径 | 做法 | 代价 | 适用 |
|---|---|---|---|
| 改设定 | 修改世界规则以容纳两者 | 可能引发连锁修改 | 新设定更好时 |
| 改情节 | 调整事件顺序或人物行动 | 影响已写正文 | 设定已定稿时 |
| 加解释 | 补一条例外条款/隐瞒/误传 | 需有铺垫，否则像补丁 | 两者都重要时 |

**补丁纪律**：用"加解释"解决冲突时，必须同时埋下伏笔（说明为什么之前没提）。凭空出现的解释，读者判定为作者改设定。

## 5. 设定状态标签

| 标签 | 含义 | 能否写入正文 |
|---|---|---|
| `[用户原始设想]` | 用户提出，未确认 | 可试探性使用 |
| `[已确认]` | 用户明确同意 | 可以 |
| `[专家建议]` | 本 Skill 提出 | 不可，需先确认 |
| `[待确认]` | 需用户决定 | 不可 |
| `[待验证]` | 需要正文/资料检验 | 谨慎，可作临时设定 |
| `[已废弃]` | 明确不用 | 不可，且不应再引用 |

**纪律**：设定集中每个条目只能有一个状态。多个状态并存说明管理失效。

## 6. 编号规则

```
前缀-三位数字：RULE-007
```

| 规则 | 说明 |
|---|---|
| 连续 | 新增取当前最大值 +1，不复用废弃编号 |
| 不复用 | 废弃的编号永久保留，标注 `[已废弃]` |
| 不重编 | 改名不改号；改名写入变更记录 |
| 引用 | 全文引用一律用编号，不用名称（名称会变，编号不会） |
| 分组 | 编号段可预留：CHAR-001~099 为主角团，100~199 为敌对势力 |

## 7. 变更记录格式

每条重要修改记一行：

| 编号 | 原内容 | 新内容 | 原因 | 来源 | 时间 | 受影响 | 版本 | 需确认 |
|---|---|---|---|---|---|---|---|---|
| RULE-003 | 异能每次消耗 1 年寿命 | 每次消耗 1 年寿命，且同一日不可用两次 | 战斗中连续使用过强 | 用户 | 2026-11-01 | CHAR-001 战斗设定、EVENT-007 | v1.1 | 否 |

**纪律**：

- 对话中的口头建议不自动成为版本更新，需用户确认后才写入。
- 每次交付附版本号与变更摘要。
- 版本号规则：结构性变更 v2.0，条款调整 v1.x。

## 8. 设定索引

当设定条目超过 30 条，必须建立索引，否则无法维护。

| 编号 | 名称 | 类型 | 状态 | 版本 | 被引用次数 | 最后修改 |
|---|---|---|---|---|---|---|
| RULE-001 | 灾变感染机制 | 规则 | 已确认 | v1.2 | 14 | 2026-11-01 |

"被引用次数"为 0 的条目，标记为候选删除项——没有实体引用它，说明它对故事无作用。

## 9. 一致性检查报告格式

```
一、检查范围
   覆盖条目数、时间跨度、人物数

二、结论
   P0：n 项 / P1：n 项 / P2：n 项 / P3：n 项
   是否可交付：是 / 否

三、P0 与 P1 明细
   编号 | 冲突描述 | 冲突双方 | 影响范围 | 建议方案（2–3 个） | 需用户决定

四、P2 与 P3 建议
   逐条列出，标注是否必须处理

五、待确认事项汇总
   集中列出所有需要用户拍板的问题
```

## 10. 交付前的最后三问

1. 把所有规则交给一个聪明的反派，他能不能赢？不能 → 规则太软，需补强。
2. 把主角换成一个普通人，这个故事还能成立吗？不能 → 世界围着主角转，需补独立运行能力。
3. 删掉任意三条设定，故事是否受损？都不受损 → 这三条是无用设定，移入预留区。
